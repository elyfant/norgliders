# Decision: pyglider `deployment.yml` is generated from OGDB per run, not hand-maintained

**Date:** 2026-09-08

**Status:** accepted — `resolve()` implemented 2026-09-09 (see below)

## Decision

The pyglider `deployment.yml` for a Slocum mission is **generated from OGDB at
processing time** and written into the mission's data folder. It is not a
hand-authored, version-controlled file. OGDB is the single source of truth for
everything in it except the processing window (and, later, QC narrative), which
are per-run decisions.

`slocum_data_processing.processing.config.resolve(mission_number)` is the
generator (currently a stub). `slocum-process-mission <N>` is the entry point.

## The flow

```
slocum-process-mission 28  [--regenerate] [--steps l0 | l1,l2 | ...]
```

1. **Locate** — glob `<data-root>/028-*`. The `NNN-` numeric prefix is the
   reliable key; `missions.internal_data_path` is populated for only ~half the
   missions and is inconsistent (mismatched folder names, `"only sbd"`, blanks),
   so it is not used as the locator. `norglider_missions.std_mission_name`
   validates the match. Require exactly one hit.

2. **Config** — if `<data_folder>/deployment.yml` is absent (or `--regenerate`):
   query OGDB (mission row, glider, science payload at `launch_date`,
   calibrations) → render via the field-map + the repo sensor catalog → write
   `<data_folder>/deployment.yml` with a provenance header:

   ```
   # GENERATED by slocum_data_processing <version> from OGDB (<db>) at <ISO-8601 UTC>.
   # OGDB is the source of truth for everything below except `processing:`.
   # Set processing.l1_time_range after inspecting L0.
   # Re-run with --regenerate to refresh the OGDB-derived fields (shows a diff first).
   ```

   `processing.l1_time_range` is seeded to `[launch_date, recovery_date + 1d]`
   so the file runs as-is. Then that file is loaded.

3. **Raw prep** — if `binary/` is missing or empty, run `rawprep` automatically
   (copy `raw/`→`binary/`, decompress, rename, cache-sync), with a log line.

4. **Process — always two runs** (D5) —
   - `--steps l0` → decode + L0 (all data)
   - *human: inspect L0 in `data_exploration.ipynb`. This is the checkpoint —
     bail here on missing cache files, bad data, missing science variables,
     etc. Set `processing.l1_time_range` in `<data_folder>/deployment.yml`.*
   - `--steps l1,l2` → windowed L1/L2

   No one-pass mode — the L0 checkpoint is deliberate on every mission.

5. **(separate) OGDB ingest** — `OGDB/scripts/ingest_slocum_mission.py` writes
   mission dates + surface track and sets `missions.l1_file` / `l2_file`.

## Sub-decisions

- **D1 — `deployment.yml` lives in the mission data folder** (working file:
  co-located with the raw data and products, carries the provenance stamp,
  regenerable). The repo does **not** carry per-mission YAMLs. One committed
  fixture is kept under `python/tests/fixtures/` purely for the `resolve()`
  regression test. `python/missions/002-…/` is deleted once `resolve()` works.

- **D2 — `--regenerate` rewrites only the OGDB-derived block.** The file is
  split into a generated section and a preserved `processing:` section (window,
  later QC notes). Regeneration diffs the generated part and asks to confirm; it
  never touches `processing:`.

- **D3 — `sensors.txt` is a repo-side facility default** (nav + engineering +
  `sci_*` — it barely changes). The generator only appends a mission's science
  sensor names if they are missing from the default.

- **D4 — raw prep runs automatically** when `binary/` is empty on a first run.

- **D5 — always run twice; no one-pass mode.** `--steps l0` then, after the
  human checks L0, `--steps l1,l2`. The L0 step is the deliberate bail-out
  point (missing cache files, bad data, missing science variables, wrong
  window). Funding: **per-project** — use the existing `projects.funder` /
  `projects.fund_number`; compose the CF `acknowledgement` attribute as
  *"This deployment was funded by {funder} under grant {fund_number}."* No new
  column. (`fund_number` population/format to be tidied — most are a specific
  Research Council of Norway grant number.)

- **D6 — `deployment.yml` needs the calibration *date* only; nothing about the
  certificate.** pyglider does not apply raw calibration coefficients — the
  Slocum applies factory cal onboard, so `sci_water_temp` / `sci_water_cond`
  etc. arrive in engineering units and pyglider only does TEOS-10 derivations
  on top. So the yaml needs `calibration_date` (= `asset_*_sensor_cal.cal_date`,
  latest ≤ launch). The `calibration_report` attribute is a bare pointer string
  that pyglider never opens — set it to an OGDB cal-record reference (id or
  portal URL) or leave it blank; **no `documents`/PDF wiring**. The parsed
  coefficients in the cal tables become relevant only in the QC phase (drift
  correction, Aanderaa optode SVU foil recalculation, thermal-lag).

- **D7 — `factory_calibrated` is derived**, not stored:
  `factory_calibrated = (asset_*_sensor_cal.calibration_facility == manufacturers.name)`.
  No schema change. (`calibration_facility` to be tidied to a fixed list with
  proper names.)

## Repo changes this requires

- Implement `config.resolve(mission_number)` — psycopg connection + ~4 queries
  (mission row via `norglider_missions` + raw FK ids; glider via
  `asset_glider_details` + `assets` + `platforms`/NVS B76; science payload via
  the recursive `asset_assignments` walk at `launch_date`; latest
  `asset_{ct,do,eco}_sensor_cal` ≤ `launch_date`) → render via the field-map.
- A **repo-side sensor catalog** keyed by sensor model that produces the
  `netcdf_variables` / `profile_variables` blocks (pyglider config schema,
  version-coupled — not OGDB's job). OGDB says *which* models; the catalog
  turns each into its pyglider entries. The NVS sensor→native-param→OG1 chain
  in OGDB remains deferred (see [[deployment-yaml-strategy]] / earlier notes).
- `slocum-process-mission`: write the YAML to the data folder; `--regenerate`
  (diff + confirm, OGDB block only); auto raw-prep on first run.
- Move the committed `python/missions/002-…/deployment.yml` to
  `python/tests/fixtures/`; `resolve(2)` must reproduce it (bar the fields OGDB
  genuinely does not model). Delete `python/missions/`.
- `DATABASE_URL` config (production via the `nrec_app` SSH tunnel, or a local
  `ogdb` snapshot).

## Reasoning

The facility principle: **OGDB is the source of truth; a workflow must not
depend on someone remembering to hand-edit a file.** A committed per-mission
YAML in the processing repo is exactly that failure mode — it drifts from OGDB,
needs PR review for a data-entry change, and duplicates facts OGDB already
holds. Generating it per run from OGDB, into the data folder, with a provenance
stamp, means the config is always a faithful projection of OGDB at a known
moment, and the only thing a human sets is the processing window — which is a
*decision made by looking at the data*, not data entry.

The one genuine split is `netcdf_variables`: that block is pyglider's
configuration format (CF names, `bar2dbar`, valid ranges), which changes with
the pyglider version, not with the glider inventory. It stays as versioned code
in the processing repo, driven by the sensor models OGDB reports.

## Implementation status (2026-09-09)

Built in `slocum_data_processing`:

- `config/processing.toml` + `settings.load_settings()` — environment (data
  root, cache dir, `DATABASE_URL`) and the `[facility]` CF constants. Env vars
  and `config/processing.local.toml` (gitignored) override.
- `processing/ogdb.py` — the read-only OGDB queries (mission row + FK joins;
  recursive `asset_assignments` payload walk at `launch_date`; latest
  `asset_{ct,do,eco}_sensor_cal`).
- `processing/sensor_catalog.py` — the repo-side model→pyglider-variable map
  (CTD / FLNTU / FLBBCD / Aanderaa 3835 / Aanderaa 4xxx) + the fixed nav and
  profile-variable blocks.
- `processing/config.py::resolve()` — assembles the deployment dict;
  `write_deployment_yaml()` renders it with the provenance header and the
  preserved `processing:` block.
- CLI: `slocum-process-mission <N> --from-ogdb [--regenerate] [--generate-only]`.

Verified: `resolve(28)` off a local OGDB snapshot (with a science-payload test
fixture) generates a `deployment.yml` that produces **byte-identical L1 science
data** to the hand-authored mission-028 config (`np.allclose` on temperature /
salinity / chlorophyll / oxygen). `python/tests/test_sensor_catalog.py` +
`test_resolve.py` cover it.

**Still pending:** the 3 OGDB schema additions above; production access
(`nrec_app` tunnel) so the payload half resolves for real missions — the local
snapshot has no `asset_assignments` for the older gliders; retiring
`python/missions/` once every active mission is generated.
